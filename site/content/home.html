DEP in five minutes.

Read the full guide (30 minutes and more) →
  1. MINUTE 1

    The problem

    Read access to a column is also the right to list, search and export it. A support tool that needs to find one customer by email gets, with the same grant, every address. Looking a person up by a value you were given is a different capability from reading values you were never given.

  2. MINUTE 2

    The idea

    Declare the column protected in the schema: email TEXT PROTECTED MATCH DOMAIN email_address. The database then treats the four operations above separately, and decides by how each query uses the value.

  3. MINUTE 3

    Use it without receiving it

    A lookup by full-value equality works, and the email comes back as NULL. Pattern matching (LIKE), ranges and sorting on the protected value are refused with ZD101, and reading the column returns NULL for every row. Try the four examples below.

  4. MINUTE 4

    Two access paths

    The endpoint a client connects through fixes its access path. Operational connections can match protected values and write. Masked read connections, such as a dashboard's, read ordinary fields and cannot match protected values (ZD102). Neither path returns a protected value in ordinary query output.

  5. MINUTE 5

    Rules are code

    These decisions live in the schema and its grants, so a team can version them, review them next to the application change that needs them, and test them: the lookup the application needs succeeds, and the query it should never run is refused. They are also decided while the database is designed and modeled, not added after the application is built. That is Privacy as Code.

How DEP differs

Why not just use PostgreSQL?

Conventional databases can protect these values, and a careful team can build a protected lookup by hand. The difference DEP explores is where the rule lives. These are the usual tools, and where each leaves the lookup problem open.

Existing toolWhat it does wellWhat it leaves open for this problem
Column privilegesChoose which columns a role may read.In PostgreSQL, filtering on a column needs the SELECT privilege on it. A role that may find a user by email can also read every email.
ViewsFix which columns and rows a query sees.A view without the email column cannot be filtered by it, so a lookup by email still needs an interface written for it. PostgreSQL views
SECURITY DEFINER functionsRun with the owner's privileges, so a function can find a person by email without giving the caller the column.It works. Each lookup is a function the team writes and secures (the documentation warns about search_path), and consumers must call it instead of writing queries.
Row-level securityRestricts which rows a user can read or change.It governs rows. Column access stays with GRANT, so it does not say how a column's value may be used.
Dynamic data maskingMasks values in query results for users without the unmask permission (for example in SQL Server).Microsoft documents that users who may run ad hoc queries can infer masked values, for example by filtering on a range.

What DEP changes

In DEP the schema declares a column protected, and the database tells the uses apart: an exact-match lookup works, pattern matching, ranges and sorting are refused, and reading the value gives NULL. The same rule then applies to every query, including one nobody wrote in advance. Exact-match lookups can still be tried repeatedly, so DEP also has match limits (ZD109) that cap how often a role may try.

DEP does not claim that other tools cannot do this. It asks whether the database can understand the rule once, in the schema, instead of each team rebuilding it for every lookup. The roadmap compares DEP with related work and states that its novelty has not been independently reviewed.

To make the rules concrete, this example uses a small clinic. Compare finding a record, reading identifiers and joining protected records with and without an anchor.

Protection starts in the schema.

Here, the national ID is the protected value. A shared match domain lets related protected columns match each other.

CREATE TABLE patients (
  patient_id  BIGINT PRIMARY KEY,
  national_id TEXT PROTECTED MATCH DOMAIN person_id,
  full_name   TEXT
);

Finding a record does not require returning its identifier. Linking the entire dataset is a separate operation.

Know the boundary

Designed to demonstrate a model.

DEP is an experimental concept and DEP Engine is experimental software. A lookup can reveal that a record exists, a disclosed value leaves the database's control, and the server stays trusted. PostgreSQL wire compatibility is not full PostgreSQL compatibility. Protected identifiers do not make other fields anonymous, and DEP does not establish GDPR compliance.
